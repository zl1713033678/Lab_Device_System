---

## 1. 业务痛点与核心场景拆解
1. 当前 `device_usage_logs` 表仅靠应用层不提供删除接口实现“Append-Only”，无法发现数据库层面的直接篡改或删行。
2. 房间重命名会修改设备当前 `room_name`，历史会话统计时若仅关联当前名称，可能导致历史归属被当前名称重解释。
3. 数据库结构变更依赖启动时零散 `ALTER TABLE`，缺乏版本化迁移与备份/恢复演练机制。

## 2. 架构与算法设计（含遵循 AGENTS.md 红线的边界约束）
- **哈希链设计**：在 `device_usage_logs` 新增 `previous_hash` 与 `hash` 字段；每条记录入库时在事务锁内读取上一条尾哈希，计算 `SHA-256(seq + prev_hash + device_code + timestamp + previous_status + new_status + raw_data)`。
- **历史快照边界**：在履历记录或会话计算中按需求决定是否固化当时的 `room_name_snapshot`，避免历史报表随房间改名漂移。
- **验签告警**：后端全链重算校验断裂点，若发现哈希不匹配或序列空洞立即返回异常定位。
- *边界约束*：在哈希链与验签落地前，对外文档与界面不得继续宣传已具备“不可篡改密码学存证”。

## 3. 数据模型与接口扩展规划
- `device_usage_logs` 扩展列：`previous_hash`、`hash`（及可选 `chain_seq`）。
- 新增接口：`GET /api/v1/audit/verify`（返回链完整度、校验条数、首个篡改断裂 ID）。
- 运维脚本/接口：独立数据目录规范、热备份与恢复校验演练。
